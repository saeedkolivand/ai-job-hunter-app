# Domain model (core types, traits, registries)

Last updated: 2026-08-13

Describes the **shape**; the source is authoritative for field-level detail. Query graphify (MCP `query_graph` / `get_node`, else `graphify explain "<type>"`) then read the owning file.

## Resume document

- **`DocumentModel`** — `apps/desktop/src-tauri/src/model/` (`document.rs`). The structured résumé: sections → blocks → rich text. The export pipeline and templates consume this; the renderer edits a serialized form via IPC.
- **Sections / blocks / rich text** — section ordering, content hierarchy, and customization are owned by `resume-export-expert`; see `model/` + `docs/EXPORT_TEMPLATES.md`.
- **Contact profile** — `contact_profile/` + `commands/contact_profile.rs` (header source of truth for links/contact). Conflict detection on résumé import: `contact_profile/mod.rs: detect_contact_conflicts` (normalizers + per-field diffing); `documents.import` returns additive `contactConflicts` / `suggestedContact` fields (loose JSON, no schema change, import never gated). Renderer resolution: `components/contact/ContactConflictModal/` surfaced from `features/onboarding/steps/ResumeStep/` and `features/settings/components/preferences/ResumePreferences/` (keep-mine / use-résumé per field). Conflict resolution is **local-only** — no data leaves the device.

## Export contract

- **`ExportRequest` / `ExportResult`** — `apps/desktop/src-tauri/src/export/types.rs` (the request/response shape: target format, template, ATS mode, locale). Owned by `resume-export-expert`; **implemented** by `pdf-docx-generator`.
- PDF path: `export/typst_engine/` (sole PDF backend — printpdf removed). DOCX path: `export/docx/`, `export/model_docx/` ([docx-rs][docx-rs]). Templates: `export/templates/`. Gate: `validate/`.

## Job / matching

- **Job posting / postings** — `jobs/`, `postings/`, `commands/jobs.rs`. The scraped/normalized job representation consumed by matching.
- **Evidence extraction** — `documents/evidence.rs`: `extract_evidence` parses a source résumé into roles, projects, and skills; `rank_bullets` scores evidence candidates against job-ad text. Consumed by: trim-panel ranking and content validation.
- **Matching** — `commands/match_resume.rs` (single on-demand `match_resume`): keywords lookup via `documents/keywords.rs` (shared module). Pipeline split: `keywords_normalized()` caches pre-stemmed tokens (language-agnostic), `apply_stemmer()` stems at match time using JD language detection (`whatlang` + Snowball per language). Tokenization: lowercase + synonym-normalize + language-detect + filter (drop ≤3 chars unless in `SHORT_TECH_TERMS` allowlist, drop stopwords). Corrupt-cache fallback: `from_str().unwrap_or_default()` returns empty set. **Translation (local-provider-only)** — `commands/translation.rs`: `TranslationCache` (session-scoped HashMap); `translate_if_needed()` detects non-English via whatlang, gates on `provider_allows_translation()` (Ollama + CLI agents like "claude-code" allowed), invokes the provider, caches result, falls back to original on any failure. Called before stemming/keyword extraction. **Keyword coverage** — `keyword_coverage()` returns resume vs job overlap %; score model is weighted blend of semantic similarity + keyword coverage (**read source for exact weights**). **On-demand scoring** — Frontend `MatchScoresProvider` requests a score per job on demand (via the single `match_resume` IPC) as rows render, distributing results per-row; the former one-pass `match_resume_batch` command was removed (zero consumers). Default: keyword-only (no embedding; `semanticScoringEnabled=false`). See ADR-020 + ADR-017 Phase K notes. Recommendations: `recommend/`. Cover letters: `cover_letter/` + `commands/cover_letter.rs`.
- **Content validation** — `validate/content/mod.rs`: deterministic checks on generated résumés/cover letters for factual errors (unsourced claims, dropped roles, altered links) and guidance issues (low coverage, AI-tell prose). Code roster + severities live in `CONTENT_ISSUE_CODES` (read the const — don't copy the count). Contracts: `ContentInput`, `ContentIssue`, `ContentReport`. Agent Read tools: `validate_resume`, `search_candidate_evidence`, `get_trim_suggestions`, `lookup_salary`.

## Generation pipeline

- **Depths** — `GenerationDepth = 'fast' | 'quality' | 'max'`; UI names **Fast / Quality / Max**. Fast is today's one-shot TS path + validators. Quality and Max are Rust-orchestrated multi-stage pipelines (Phases 2–4). See [ADR-032](decision-records/adr-032-generation-pipeline-ownership-and-rule-enforcement.md) for the core rule (LLM decides HOW, never WHAT) and mechanical enforcement via Rust structures.
- **Quality depth** (Phase 3, shipped) — 4-call pipeline: analyze_job → match_evidence → strategy → draft → validate → repair (≤2 rounds). Each call re-anchors to the source resume; prior-stage output is untrusted (fenced via ADR-010). Criticals only from deterministic checks (Rust compares against source; model never emits Critical). Terminal fabrications go to a per-bullet review panel (keep/remove user decides; nothing silently dropped).
- **Max depth** (Phase 4, shipped) — quality with the single draft replaced by one structured call per section (summary, skills, one per company plus a condensed "earlier roles" group, projects, education), assembled into the same plain-text body every other depth produces, then validate → repair → judge. Ceilings, the stage list and the section-key grammar are owned by `pipeline::resume::MAX_STAGES`, `Budget::RESUME_MAX` and `SectionKey` — read them there; copies of those numbers have already drifted once. What is worth knowing at this level: identity (company/title/dates) is SEEDED from the source and never model-authored, the judge is Warning-only and skippable, and strategy + evidence artifacts persist at max depth only so a per-entry regenerate can rebuild one role without a new run.
- **Run store** — `pipeline_runs.db` (separate from `ai_generations`); immutable history (status, stopped reason, metrics, stage trail). Per-job retention: newest 3 runs. Lifecycle: queued → running → completed|needsReview|failed|cancelled. IPC: run(req) → {runId, jobId}; get(runId) → detail; listForJob(jobUrl) → summaries[≤3]; regenerateSection / resolveFabrication mutate per-run state.
- **Quality report** — deterministic content validators run after every generation (fast, quality, max alike). Report lives in `ai_generations.quality_report` column (JSON wrapper carrying per-document ContentReport + per-bullet verdicts). Staleness detected via source-text-hash. Verdicts round-trip through user edits (keep/remove per issue; unfabricated claims remain unflagged). The renderer's `quality-report.ts` (`parseQualityReport`, `mergeRecheckedReport`) enforces: incoming slots replace stored slots WHOLE, so preserved fabrication verdicts must be carried forward from the previous slot on re-check.
- **Document divergence** (Phase 3, resolved) — a run row is immutable history; the aggregate résumé + report are live state (join on `job_url`). Verdict persists across the move (a later run, `regenerateSection`, re-check, or hand edit may change the document; report records by issueKey, reads no text, so verdicts land afterward). The merge rule (`merge_quality_report` per TOP-LEVEL key) means incoming slots replace stored slots WHOLE; renderer's `mergeRecheckedReport` preserves previous slot's extra keys (fabrications, verdicts) across re-checks.
- **Fabrication verdict semantics** — not an event, not state, but **intent matched against fact**. `decision: 'remove' | 'keep'` records user intent; `resolved` is true only when intent and document agree (keep → settled; remove → settled when evidence absent). Marked-for-removal lines are applied through the host's ordinary edit/save path (never silently); a recorded-but-unapplied removal renders its state and cannot read clean.
- **Core rule enforcement** (ADR-032) — (1) evidence grounding: LLM ranks, Rust drops non-verbatim + overwrites status; (2) company roster lock: model seeded from source, never re-dates/drops roles; (3) deterministic validation: 0 provider calls, every Critical is a Rust comparison against source. Prompt codegen (pnpm gen:prompts) freezes pure `(lang)→string` outputs into Rust (`FACTUAL_GROUNDING_RULES`, etc.); same lexicon instructs model + validates output (single source). See also [ADR-033](decision-records/adr-033-no-model-written-agent-memory.md) (no model-written agent memory; all persistence is immutable, user-verifiable).

## Referrals

- **`referrals` store** — `referrals/mod.rs` (L1 domain); full CRUD via `commands/referrals.rs`. Each record captures a contact (name, company, role, relationship) plus a generated or hand-edited referral note in up to three formats (email, LinkedIn message, cold-ask). Local-only — no data leaves the device.
- **`ReferralModal`** — `apps/desktop/src/renderer/features/documents/components/TailorFlow/ReferralModal/`; surfaced in the tailor/apply flow.
- **Prompt layer** — `buildReferralPrompt` / `buildReferralImprovePrompt` in `packages/prompts` produce templates; `generateReferral` (renderer `lib/generate/`) streams referral text via `gen.improve()`, producing connection-note (≤ 300 chars), email, and LinkedIn-message variants. **Improve variant** — free-text instruction (warmer/shorter/more specific/fix grammar) streams a revised draft via the same streaming infra.
- **Data lifecycle** — wired into `manage_resettable` (full reset) and `commands/data.rs::build_bundle` (export/import). See [ADR-011](decision-records/adr-011-referral-helper-manual-only.md) for the decision to keep entry manual and discard LinkedIn scraping.

## Application tracking

- **`applications` aggregate** — `apps/desktop/src-tauri/src/applications/mod.rs` (`ApplicationStore`); identity, user-mutable status lifecycle, contact/tracking metadata, an imported/pasted job description (extracted and byte-clamped at import; partial imports become stubs), and an append-only status-event history. A Generation is zero-or-one child. See [ADR-007](decision-records/adr-007-ai-generations-application-aggregate.md).
- **`ai_generations` (now child)** — `ai_generations/mod.rs` (`AiGenerationStore`); a produced artifact (résumé + cover-letter text, mode, languages). Formerly the aggregate root; now a child Document of Application (refs via `application_id`). Per-job merge-upsert by `job_url` (single row carries both texts). See [ADR-007](decision-records/adr-007-ai-generations-application-aggregate.md).
- **Auto-track entry points** — Application status is auto-set via extension form-submit watching (`extension_bridge/status_update.rs`, opt-in flag #687) and email-confirmation watching (`email_watch/`, ADR-0013). Manual enrichment via `commands/autopilot.rs: enrich_applied` for found-job imports.
- **Email confirmation watching** — `email_watch/` + `email_watch_scheduler.rs` (IMAP polling, confirmed-application detection, ADR-0013). See [notification-center.md](notification-center.md) for the notification output.

## AI / providers

- **Provider adapters** — `commands/ai_provider/{ollama,ollama_cloud,openai,anthropic,gemini,cli_agent}.rs` behind a shared interface (`mod.rs`); business logic must not depend on a specific provider. Provider, model, and base_url are resolved by the backend-owned `ai_config/` module (AiConfigStore, see ADR-0012 for provenance rules) — never renderer-supplied.
- **Per-stage model resolution** — `ai_config/stage_overrides.rs` + `pipeline/mod.rs::Completer::from_active_for_stage`. User can override provider + model for individual stages (analyze_job, match_evidence, strategy, draft, judge, and per-section generations) via `ai_stage_overrides` table (PRIMARY KEY = stage name). Free stages (assemble, validate) reject overrides. Resolution: (1) WRITE: validated through the same chain as active config (`ProviderId::parse` → `validate_model` → `base_url` via `net::ssrf`); (2) READ/resolve: validated again by `from_active_for_stage` because store can be restored from backup. "Absent" is always readable as "user did not set this" — never a silent inference or default applied. **No per-stage `base_url`** (design choice): endpoint is a provider property and already stored in that provider's own row; per-stage copy would be invisible in Settings and create a covert channel (never under user control). Context window (`options.num_ctx`) rides on each override row as the model's property, not the run's. Default `None` = provider's own default, never guessed. Read source: `ai_config/stage_overrides.rs` § type doc (Never a silent switch) + validation and read-side re-validation chains.
- **Per-stage cache keys** — `pipeline/resume/cache.rs::StageCacheKey`. Cache key includes provider + model + rolling upstream artifact hash so per-stage routing changes invalidate correctly. Each stage extends the key with its own artifact before passing to the next, so downstream stages include all upstream decisions in their identity. Caching only applies to pure-function stages (analyze_job, match_evidence, strategy); draft/validate/repair/judge never cached.
- **Embeddings** — `documents/mod.rs` (storage + embedding-space invalidation on model change).
- **Prompts** — `packages/prompts` (provider-aware, locale-driven templates).
